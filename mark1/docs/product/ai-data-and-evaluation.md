# V investigator: provider-neutral implementation and data plan

22 November 2026. Synthetic demo only. No provider/model has been selected, called or trained.

## Implemented boundary

`mark1/ai/engine.py` implements `propose(request)` against the canonical v2 schemas. A supplies a current authorized catalog, observations and conversation context. A separately supplies an optional async `read_image(handle)` callback bound to the authenticated caller and current inference; V never receives a bearer token, filesystem path, public image URL or database tool. Cleared bytes are hash-checked before encoding as model input.

The model selects one structured decision: supported identity candidates, a view, question, check, explanation or escalation. Request/session/revision/hash bindings are attached by the engine, not generated by the model. The response schema is derived directly from A's canonical proposal schema. A independently validates scope, lifecycle, prerequisites, evidence and claims before returning any canonical guidance to J.

The engine makes at most one provider call per request and exposes zero tools. It rejects exhausted budgets and expired deadlines before calling a provider, respects the original absolute deadline with an async timeout, propagates cancellation, caps output at 16 KiB, rejects duplicate fields/extra keys/non-JSON output and has no retry or fallback model. A provider error/refusal/invalid response produces MODEL_FAILURE escalation; a deadline/budget failure produces BUDGET_EXCEEDED. Only counts and safe outcome enums are logged.

The small scoped catalog is supplied directly as context. No second catalog store, vector database, embedding pipeline or model-side retrieval is needed for this increment. Source authority and publication remain A-owned; production content remains V/SME work.

## Provider adapter handoff

`ProviderAdapter(model_config_version, generate)` accepts a cooperative async callable. It receives these keyword arguments:

- `messages`: system text plus one user message with `content` blocks. Text blocks are `{type: "text", text: ...}`. Image blocks are `{type: "image", image_id: ..., mime_type: ..., data: ...}` with base64 bytes. These are neutral internal blocks, not a particular SDK's wire format.
- `output_schema`: the canonical kind/payload decision schema, including conditional payload definitions.
- `max_output_tokens`: 2048.
- `deadline_at`: the original UTC deadline. HTTP/SDK timeouts and any internal calls must remain inside it.

Return exactly one JSON string containing `kind` and `payload`. Refusal/invalid output is handled safely; adapters may also return a schema-valid ESCALATE decision. No arbitrary model prose reaches the UI. A future adapter must translate the neutral blocks/schema into its provider's supported request format and must not silently drop images or schema constraints. Credentials remain server-side; do not add them to VITE variables, prompts or logs.

Inject it using `create_app(settings, provider=ProviderAdapter(...))`. Passing both `engine` and `provider` is rejected. The existing `create_app(settings, engine=...)` interface still works. `python -m uvicorn mark1.server.app:create_app --factory` still starts the deterministic stub; this increment adds no live-provider configuration or SDK dependency. A configured provider reports `structured-investigator` at `/health`, while the data mode remains synthetic-demo-only.

The injected generator must genuinely await async I/O. Wrapping a blocking SDK in `async def` does not make it cancellable. The existing backend invalidates stale inference results after new input/stop; provider adapters must additionally obey cancellation and never keep an unbounded hidden tool loop. No live inference resource/cost behavior has been measured here.

## Do we need training data?

No custom training is required to implement this boundary. Start with a pretrained vision model once one is selected; supply approved knowledge and evaluate it before considering fine-tuning. Fine-tuning is a later option only if held-out failures show a repeatable gap that better knowledge, prompts or image capture do not fix. It cannot replace backend policy or establish repair truth.

| Data type | Required now? | Purpose |
| --- | --- | --- |
| Approved knowledge/catalog | Yes | Supported models/configurations, external checks, view/question/explanation templates, diagrams, applicability, source rights and versions |
| Fictional labeled development cases | Yes | Exercise readable/unreadable labels, wrong-valid configuration, unavailable views, absent diagrams, contradictions, insufficient evidence and escalation |
| Frozen held-out evaluation cases | Before selecting/enabling a live model | Measure actual perception, useful next-step selection, unsafe suggestions, evidence grounding, refusals, latency and cost |
| Fine-tuning examples | Not for this increment | Consider only after measured model failures justify the work and rights/labels are approved |

Current assets are A's canonical synthetic catalog, source text and scenario fixtures under `docs/specs/Mark1-Team-Spec/contracts/`, plus generated snapshots in tests. They are integration inputs, not a trained model or a held-out perception benchmark. Scripted provider responses test the boundary; they do not demonstrate visual understanding, investigation quality or prompt-injection resistance of a live model.

## Evaluation and data collection before model selection

Use fictional/generated content only. Do not connect to a real vault or collect/send real customer images or documents in this repository. V authors new versioned content; A publishes it. Real technical correctness would need separate rights, environment and independent SME labels.

Freeze a manifest by device/session/scenario/source before prompt tuning. Record generated image ID/hash and generation method, readable label/configuration or explicit unknown, camera conditions (crop/glare/blur), supported scope, expected next-action set, required evidence, refusal/escalation labels, split and rights. Keep near-duplicate frames and variants from one session in the same split. Never use human confirmation as a substitute for measuring raw wrong-valid identity candidates.

Compare the selected model against both the current deterministic engine and a static approved checklist. Report raw exact identity, wrong-valid candidates, coverage/refusal, human corrections, useful/redundant/unsafe view requests, grounded claims and diagram nodes, contradiction/escalation, steps, median/tail latency and actual token/call cost. Include all failures and exclusions. The existing proposed G2 gate requires at least 100 held-out images; this implementation does not supply that dataset or close G2/G4.

Flow-only explanations, typed visual findings and correction/amendment commands remain open contract refinements (AR-01..03). No online learning, automatic repair confirmation or diagnostic accuracy claim is introduced.
